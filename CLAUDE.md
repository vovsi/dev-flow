# CLAUDE.md — DevFlow

Инструкции для Claude Code по работе с этим проектом. Следуй им при любых правках.

## Суть проекта

Одностраничное приложение-чек-лист для рабочего процесса разработчика по задаче Jira:
вставил ссылку на задачу → приложение нашло/создало задачу в своей БД → показало чек-лист
из стандартных шагов разработки (Story Points → ветка → PR → ревью → Jira → трек времени →
отправка PR) → каждый пункт при выполнении помогает сделать сопутствующее действие
(скопировать текст/команду, попросить ввести ветку/ссылку на PR) и отмечается галочкой.

Рассчитано на постоянное использование в маленьком окне браузера (см. README.md) как
персональный трекер рутины по задаче, а не на многопользовательскую нагрузку — БД
локальный SQLite-файл, авторизации нет, это осознанно (см. YAGNI ниже).

**Целевое разрешение окна — 500×500 пикселей.** Весь дизайн (макеты, модалки, отступы,
переносы текста и кнопок) должен идеально выглядеть именно в этом размере — это основной,
а не крайний случай использования. Проверяй разметку в вьюпорте 500×500 при любых
визуальных правках, а не только на широком экране разработки.

## Стек

- PHP 8.3, без фреймворка и без Composer (масштаб проекта не оправдывает зависимости)
- SQLite через PDO
- Frontend: чистый HTML/CSS/JS (ванильный, без сборщиков и фреймворков), один файл `app.js`
- Docker (`php:8.3-cli-alpine` + `pdo_sqlite`) для запуска без локального PHP

## Принципы разработки — обязательны при любых изменениях

- **SOLID** — особенно единственная ответственность: репозитории только читают/пишут БД,
  сервис только оркестрирует бизнес-правило, API-файлы только разбирают HTTP и зовут сервис/репозиторий.
- **DRY** — общая логика вынесена (например `api/_bootstrap.php`, `notifyCopied()`,
  `showModal()` с параметризацией вместо копипаста модалок).
- **KISS** — простое решение предпочтительнее «гибкого». Здесь нет роутера, ORM,
  DI-контейнера — они не нужны при таком размере проекта.
- **YAGNI** — не добавлять авторизацию, миграционный фреймворк, API-версионирование,
  мультипользовательность и т.п., пока это не запрошено явно.
- **Паттерны проектирования — где это оправдано, не ради самих паттернов.** Используемые
  сейчас и их обоснование — в разделе «Паттерны» ниже. Не вводи новый паттерн, если задачу
  проще решить прямым кодом.
- **Никаких чувствительных и «своих» данных в коде — всё в `config/params.ini`.**
  Правило обязательное и без исключений: если значение относится к конкретному человеку,
  команде, компании или инстансу сервиса — оно идёт в `params.ini` (файл не в git), а в коде
  остаётся только чтение через `Config` и, если это уместно, безопасный дефолт. Что именно
  сюда попадает:
  - креды и всё, что их заменяет: токены, API-ключи, пароли, логины, почты, Basic-Auth-пары;
  - адреса и хосты внешних сервисов и инстансов (Jira, нейронка, любые публичные API),
    включая `localhost`/IP машины разработчика;
  - персональные идентификаторы: ники в GitHub/Telegram/Jira, account id, имена ревьюверов;
  - названия репозиториев, проектов, окружений и веток команды, названия статусов и
    кастомных полей Jira — то, что у другой команды называется иначе;
  - куски текстов/промптов, содержащие всё перечисленное выше (шаблоны сообщений,
    системные промпты, инструкции ревью).
  Не попадает: технические константы, не зависящие от команды и окружения (шаг ползунка,
  TTL кэша, лимиты, CSS-размеры) — их место в коде.
  Порядок при добавлении такого значения: ключ в нужную секцию `config/params.ini.example`
  (с комментарием, что это и что будет, если не задать) → геттер в `src/Config.php` с
  дефолтом или явной ошибкой → на фронт, если нужно, только через
  `window.DEVFLOW_CONFIG` в `public/index.php` → описать в разделе «Конфигурация» ниже и в
  `README.md`. Фичу, для которой значение не задано, отключаем молча (как Jira/LLM), а не
  роняем приложение. Заметил такой хардкод в существующем коде — вынеси его, даже если
  задача была про другое.
- Комментарии в коде — **на русском**, и только там, где неочевидно «почему» (скрытое
  ограничение, бизнес-правило, обходной путь). Не описывай комментарием то, что и так понятно
  из кода.
- **`README.md` держим актуальным — это часть задачи, а не отдельная просьба.** README —
  инструкция для человека, который проект не знает: он должен по нему поднять приложение с
  нуля. Появился новый ключ конфига, новая интеграция, новый внешний сервис, изменился порядок
  запуска, поменялось поведение шага чек-листа или список пунктов — правь README в том же
  коммите (разделы «Checklist steps», «Configuration», «Verify everything is up»,
  «Troubleshooting»). Описание архитектуры и внутренних правил остаётся здесь, в `CLAUDE.md`;
  в README идёт только то, что нужно пользователю для запуска и настройки.
- **README пишется на английском** — в отличие от `CLAUDE.md`, комментариев в коде и
  интерфейса. Названия пунктов чек-листа и кнопок цитируй так, как они выглядят в интерфейсе
  (по-русски), с переводом в скобках — иначе читатель не найдёт их на экране. Скриншоты —
  `docs/screenshot-light.png` / `docs/screenshot-dark.png`, окно 500×500; перерисовывай их,
  если экран чек-листа заметно изменился.

## Архитектура

Классический трёхслойный backend без фреймворка:

1. **База данных** (`database/schema.sql`, `src/Database.php`) — SQLite-файл, схема и
   сидинг/миграция пунктов чек-листа.
2. **Репозитории и сервис** (`src/*.php`) — вся бизнес-логика и SQL. Ничего не знает про HTTP.
3. **API** (`api/*.php`) — тонкий слой: разобрать JSON-запрос → вызвать репозиторий/сервис →
   вернуть JSON. Никакой бизнес-логики внутри `api/*.php` не быть не должно — если чувствуешь
   потребность написать SQL или условие бизнес-правила прямо в `api/*.php`, это сигнал вынести
   его в репозиторий/сервис.
4. **Frontend** (`public/`) — одна страница, без роутинга и SPA-фреймворка. Общается с backend
   через `fetch()` к `api/*.php`, ходит по относительным путям (`../api/...`), поэтому
   документ-рут для сервера — **корень проекта**, а не `public/` (см. README.md).

### Паттерны, используемые в коде, и почему

- **Singleton** — `Database::connection()`. Одно соединение с SQLite на процесс,
  инкапсулирует миграции при первом обращении. Тот же приём (ленивый статический кэш) — у
  `Config::load()` для `config/params.ini`, только без соединения с внешним ресурсом.
- **Repository** — `TaskRepository`, `ChecklistRepository`. Изолируют SQL от остального кода;
  если менять СУБД или схему — трогать нужно только их.
- **Service (оркестрация use-case)** — `TaskService::findOrCreateByLink()`. Инкапсулирует
  правило «если задача уже была в БД — вернуть её текущий чек-лист как есть, если новая —
  создать пустой», не заставляя `api/task.php` знать детали. Тот же принцип на уровень ниже —
  `JiraSyncService` (оркестрирует `JiraClient` + `TaskRepository`; опциональность интеграции с
  Jira инкапсулирована в фабричном методе `JiraSyncService::createFromConfig()` — без настроенной
  Jira `TaskService` получает `null` вместо сервиса и просто пропускает шаги синхронизации,
  не роняя открытие задачи).
  Так же устроен `DashboardService` (показатели дашборда): бизнес-правило «зависшая задача =
  дольше `[dashboard].stale_pull_request_hours` **рабочих** часов в статусе Pull request» живёт
  в нём, а не в `api/dashboard.php` (там же и отсчёт порога с пропуском нерабочих дней —
  `staleCutoff()`), и опциональность Jira инкапсулирована в том же фабричном методе
  `createFromConfig()`.
  **Новый числовой показатель — это метод-расчёт + строка в `DashboardService::metrics()`**,
  эндпоинт при этом не меняется.
  Тот же фабричный метод (опциональность через `createFromConfig()` → `null`, если секция
  конфига не заполнена) — у `ClaudeHooksService` (тумблер уведомлений Claude Code, `[claude]`):
  единственный Service в проекте, который не оркестрирует HTTP-клиент, а читает/пишет чужой
  файл — `settings.json` Claude Code десктопного приложения на хосте, смонтированный в
  контейнер отдельным volume (см. «Конфигурация» и docker-compose.yml).
- **Client (транспорт без бизнес-логики)** — `JiraClient` (Jira REST API v2, Basic Auth
  email+token), `LlmClient` (локальная нейронка / LM Studio, `POST <host>/api/v1/chat`),
  `AnthropicLlmClient` (Claude, `POST https://api.anthropic.com/v1/messages`, заголовки
  `x-api-key` + `anthropic-version`), `ExchangeRateClient`
  (курс USD→валюта из `[currency]`, файловый кэш `storage/exchange_rate_cache.json` на 6 часов,
  при недоступности сервиса — cache-aside: отдаётся последний закэшированный курс; кэш от другой
  валюты игнорируется — в файле рядом с курсом лежит её код),
  `QuoteClient` (случайная цитата, бесплатный публичный API без ключа,
  **без кэша намеренно** — цитата должна быть новой при каждом показе; слишком длинная для окна
  500×500 цитата перезапрашивается до `MAX_ATTEMPTS` раз). Каждый Client не знает, из-за какого
  сценария использования его вызвали. **Ни у одного Client адрес внешнего сервиса не зашит в
  код** — URL/хосты и токены приходят в конструктор из `Config` (`[atlassian]`, `[llm]`,
  `[services]`), дефолты — в `Config`, а не в самих клиентах.
- **Один Client + N Service с разными промптами (LLM-интеграция, DRY)** — клиент нейронки ничего
  не знает о конкретных промптах, только шлёт системный промпт + ввод и разбирает ответ. Поверх
  `LlmClientInterface` — пять тонких Service, у каждого свой
  фиксированный системный промпт под одну задачу: `BranchNameService` (имя git-ветки, пункт
  `git_branch`), `CommitMessageService` (первая строка commit message, пункт `code_written`),
  `DeployInstructionService` (инструкция выливки для PR), `PrDescriptionService` (описание PR
  по шаблону команды, пункт `pr_description`; единственный Service, который поверх клиента
  нейронки использует ещё один Service — дописывает результат `DeployInstructionService` в конец описания,
  и только если инструкция выливки реально введена),
  `MotivationQuoteService` (перевод цитаты для модалки поздравления, см. бизнес-правила — тут
  нейронка не автор текста, а только переводчик поверх `QuoteClient`, и клиент нейронки для него
  опционален: без настроенной `[llm]` сервис отдаёт оригинал на английском).
  Конфиг для всех пяти один — `Config::llm()` (`[llm]` в `config/params.ini`), а сам клиент все
  пять получают из `LlmClientFactory::createFromConfig()`. **Service-ы типизированы по `LlmClientInterface`,
  а не по конкретному клиенту** — иначе смена провайдера потребовала бы
  правок в каждом из них. Добавляя новую LLM-фичу — не пиши новый HTTP-клиент, добавь ещё один
  Service поверх `LlmClientInterface`.
- **Factory Method для выбора провайдера нейронки** — `LlmClientFactory::createFromConfig()`:
  `[llm].provider` = `anthropic` → `AnthropicLlmClient`, `lmstudio` → `LlmClient`. Знание о
  провайдерах живёт в одном месте, `api/generate_*.php` про него не знают вообще (тот же приём,
  что у `JiraSyncService::createFromConfig()`). **Появится третий провайдер — добавляй клиента
  и ветку в фабрику, а не условие в эндпоинтах.**
- **Identifier decoupled from position (стабильный `code`)** — у каждого пункта чек-листа
  есть неизменяемый `code` (например `git_branch`), отдельно от `id`/`sort_order`. Бизнес-правила
  (`ChecklistRepository::ALWAYS_DONE_ON_RESET_CODES`) и фронтовые обработчики (`ITEM_HANDLERS` в
  `app.js`) привязаны к `code`, а не к порядку/числу — так пункты можно свободно добавлять,
  удалять и переставлять в `Database::CHECKLIST_ITEMS`, не боясь сломать уже проставленные
  галочки существующих задач и не трогая остальной код. **Это ключевой инвариант проекта —
  не привязывай новую логику к порядковому номеру или id пункта, только к `code`.**
- **Strategy/Command map** (`app.js`) — `ITEM_HANDLERS` и `GIT_ACTION_COMMANDS` — это карты
  `code → функция`, а не цепочка `if/switch`. Добавление нового поведения = добавление новой
  записи в объект, без правок остального кода.

Если в будущем список эндпоинтов или обработчиков пунктов вырастет настолько, что текущая
плоская структура станет неудобной — тогда, и не раньше, стоит рассмотреть выделение
отдельных классов-обработчиков (Command-объекты) или простой роутер. Пока для этого нет
оснований (YAGNI).

## База данных

```sql
tasks(id, task_link UNIQUE, task_id, title, description, story_points_set, git_branch,
      claude_code_skill_mode, stat)
checklist(id, code UNIQUE, title, sort_order)
task_checklist(id, task_id, checklist_id, is_done, UNIQUE(task_id, checklist_id))
```

- `tasks.task_link` / `tasks.task_id` — по ним ищется существующая задача (`TaskRepository::findByLinkOrTaskId`).
- `tasks.title` / `tasks.description` — заголовок и описание из Jira, перечитываются при
  каждом открытии задачи (`syncJira()`, см. бизнес-правила ниже); используются также как вход
  для LLM-генерации (`BranchNameService`, `CommitMessageService`).
- `tasks.story_points_set` — признак того, что в самой задаче Jira Story Points уже проставлен,
  обновляется при каждой синхронизации — см. правило показа пункта `story_points` ниже.
- `tasks.git_branch` — сохраняется независимо от чек-листа, показывается внизу экрана
  всегда, если задано (не зависит от состояния пункта «Создать ветку в Git»).
- `tasks.claude_code_skill_mode` — режим «часть шагов делает скилл Claude Code» для этой
  конкретной задачи, `1`/`0`, по умолчанию `1` у каждой новой задачи (схема, не код —
  `INSERT INTO tasks` не проставляет её явно). Переключается в настройках приложения (раздел
  «Эта задача», виден только пока задача открыта) через `TaskRepository::updateClaudeCodeSkillMode()`
  и `api/toggle_claude_code_skill_mode.php` — см. бизнес-правила ниже. Раньше был общей настройкой
  `[mode].claude_code_skill_mode` в `config/params.ini`; теперь у каждой задачи своё значение,
  и `Config` про этот режим ничего не знает.
- `checklist.code` — единственный стабильный идентификатор смысла пункта, см. выше.
- `checklist.sort_order` — порядок отображения; можно менять свободно.
- `task_checklist.is_done` — состояние конкретного пункта у конкретной задачи.

Курс валют для расчёта заработка (`ExchangeRateClient`) кэшируется не в SQLite, а в отдельном
файле `storage/exchange_rate_cache.json` (`{rate, fetched_at}`, TTL 6 часов) — это не часть
постоянной схемы задач/чек-листа, поэтому в таблицы не попадает.

Список пунктов чек-листа — **единственный источник правды**: `Database::CHECKLIST_ITEMS`.
При каждом запросе к БД (`Database::migrate()`) этот массив синхронизируется в таблицу
`checklist` через upsert по `code` (`seedChecklist`) и удаляет пункты, которых больше нет в
массиве, вместе с их отметками (`pruneRemovedItems`). **Чтобы добавить, удалить или
переименовать пункт чек-листа — правь только этот массив.** Ничего больше менять не требуется.

## Конфигурация (`config/params.ini`)

Не в git, читается лениво и кэшируется на процесс через `Config` (см. «Паттерны» выше). Шаблон
с описанием всех ключей — `config/params.ini.example`. Секции:

- **`[atlassian]`** — `base_url`/`email`/`api_token` (обязательны для любой Jira-интеграции;
  без них `JiraSyncService::createFromConfig()` возвращает `null`, и все Jira-фичи молча
  отключаются, не ломая открытие задачи), `story_points_field` (ID кастомного поля Story Points,
  по умолчанию `customfield_10016`), `doing_status`/`pull_request_status` (названия статусов
  для переходов, по умолчанию `Doing`/`Pull request`).
- **`[worktime]`** — `start`/`end`/`daily_hours`/`lunch_start`/`lunch_end`, разбор и дефолты —
  `Config::workTime()` (см. использование в ползунке трека времени во Frontend ниже).
  `daily_hours` также используется как порог показа модалки поздравления (см. бизнес-правила).
  Отдельно от них — `non_working_days` (`Config::nonWorkingWeekdays()`, дефолт
  `Config::NON_WORKING_WEEKDAYS_DEFAULT` = сб и вс): дни недели, которые не идут в счёт часов
  «зависания» задачи у показателя дашборда. Формат — `sat, sun` (или номера ISO-8601 `6, 7`,
  разбор — `Config::parseWeekday()`); ключ задан пустым — не пропускается ни один день,
  перечислены все семь — список игнорируется (иначе отсчёт порога не сошёлся бы никогда).
- **`[dashboard]`** — `stale_pull_request_hours` (`Config::stalePullRequestHours()`, дефолт
  `Config::STALE_PULL_REQUEST_HOURS_DEFAULT` = 24): сколько **рабочих** часов задача может
  висеть в статусе `[atlassian].pull_request_status`, прежде чем попасть в показатель
  «зависшие PR». Некорректное значение (не число, ≤ 0) молча заменяется дефолтом. Новый
  числовой показатель со своим порогом — ещё один ключ этой секции, а не константа в
  `DashboardService`.
- **`[llm]`** — какая нейронка генерирует тексты. `provider` выбирает провайдера:
  `anthropic` — Claude (`anthropic_api_key` обязателен, `anthropic_model` необязателен,
  по умолчанию `Config::LLM_ANTHROPIC_MODEL_DEFAULT` = `claude-haiku-4-5` — задачи тут на пару
  строк, платить за более дорогую модель не за что), `lmstudio` — LM Studio и совместимые серверы
  (`lmstudio_host` + `lmstudio_model`, протокол `POST <host>/api/v1/chat`). Не задан `provider` —
  `lmstudio`. **Настройки обоих провайдеров лежат в секции одновременно и переключаются одной
  строкой `provider`** — при добавлении новых ключей провайдера сохраняй этот принцип, не
  заставляй удалять настройки другого. `Config::llm()` отдаёт их уже нормализованными
  (`provider` + `model` + специфичный ключ), поэтому ни фабрика, ни клиенты конфиг не разбирают.
  Провайдер не настроен — `Config::llm()` бросает исключение, четыре из пяти LLM-эндпоинтов
  отвечают 502; `generate_motivation_quote.php` переживает это (нейронка там только переводчик)
  и отдаёт цитату на языке оригинала.
- **`[github]`** — `reviewers` (список ников через запятую) для флага `--reviewer` в команде
  `gh pr create` на шаге `pull_request` (`Config::githubReviewers()`, прокидывается на фронт
  через `window.DEVFLOW_CONFIG.githubReviewers` в `public/index.php`). Не задано — флаг просто
  не добавляется в команду.
- **`[git]`** — `rebase_targets`: пункты «Rebase …» в дропдауне git-команд у названия ветки,
  формат `Подпись:базовая-ветка` через запятую (`API3:main, Adminka:dev`). Названия
  репозиториев и их базовые ветки — данные конкретной команды, поэтому в коде их нет:
  `Config::gitRebaseTargets()` → кнопки рисует `public/index.php` (`data-action="rebase"`,
  `data-base="<база>"`), а команду собирает единственный обработчик
  `GIT_ACTION_COMMANDS.rebase` в `app.js`. Не задано — пунктов rebase в дропдауне просто нет,
  `Create Branch`/`Push` остаются.
- **`[templates]`** — специфичные для команды куски текстов, которые нельзя зашивать в код:
  `review_skip_migration_repos` (репозитории без миграций, перечисляются в промпте пункта
  `claude_review` как исключение; не задано — блок «Важное исключение» в промпт не попадает,
  см. `buildReviewMigrationsExceptionBlock()` в `app.js`). Уходит на фронт через
  `window.DEVFLOW_CONFIG`.
- **`[docs]`** — ссылки на внутреннюю документацию команды, которые промпт Claude-ревью
  подставляет рядом с соответствующими пунктами: `php_code_style`, `testing_standards`,
  `api_data_format` (`Config::reviewDocLinks()` → `window.DEVFLOW_CONFIG.reviewDocLinks` →
  `reviewDocRef()` в `app.js`). Адреса конкретного инстанса Confluence, поэтому в коде их нет;
  ключ не задан — ссылка в промпт просто не подставляется, сам пункт остаётся.
- **`[salary]`** — `monthly_usd`/`working_days_per_month` (дефолты 1500/21,
  `Config::SALARY_DEFAULTS`) для расчёта часовой ставки (`Config::salaryHourlyRateUsd()` =
  `monthly_usd / (working_days_per_month * daily_hours)`) — единственный потребитель:
  `EarningsService` в модалке поздравления.
- **`[currency]`** — `code` (код валюты для курса USD→X у `ExchangeRateClient`) и `label`
  (подпись рядом с суммой, «грн»); дефолты `UAH`/`грн` — `Config::CURRENCY_DEFAULTS`.
  Подпись уходит на фронт в ответе `api/calc_earnings.php` (`currency_label`), **а не зашита
  в `app.js`** — меняя валюту, правь только конфиг.
- **`[services]`** — адреса внешних сервисов без ключей: `exchange_rate_url` (курс валют,
  база USD) и `quotes_url` (случайная цитата); дефолты — `Config::SERVICE_URL_DEFAULTS`.
  Сервисы с токенами живут в своих секциях (`[atlassian]`, `[llm]`) и сюда не переезжают.

- **`[claude]`** — тумблер «Уведомления» в разделе «Claude» настроек приложения (иконка
  шестерёнки). `telegram_bot_token`/`telegram_chat_id` обязательны — без них
  `Config::claudeNotifications()` бросает исключение, `ClaudeHooksService::createFromConfig()`
  ловит его и отдаёт `null`, раздел «Claude» на фронте не показывается вовсе (тот же приём, что
  у `[atlassian]`/`[llm]`). `notification_text`/`stop_text` — необязательные тексты сообщений
  Notification/Stop, дефолты — `Config::CLAUDE_DEFAULTS`. `settings_path` — путь к
  `settings.json` **глазами контейнера**, не хоста (по умолчанию `/claude/settings.json`);
  сам файл — это `~/.claude/settings.json` реального пользователя на хосте, смонтированный в
  docker-compose.yml отдельным volume (`${HOME}/.claude/settings.json:/claude/settings.json`,
  не через `${HOME}` в самом `params.ini` — ini-файл переменные окружения не разворачивает).
  Тумблер не хранит состояние отдельно — «включено» проверяется по факту наличия непустого
  ключа `hooks` в файле (`ClaudeHooksService::isEnabled()`), включение перезаписывает `hooks`
  блоком из двух хуков (`Notification`, `Stop`, каждый — команда `curl` в Telegram Bot API),
  выключение удаляет ключ `hooks` целиком, не трогая остальной файл. **Единственная фича
  проекта, которая пишет за пределы контейнера** — см. «Безопасность» про то, почему
  смонтирован только сам файл, а не весь `~/.claude`.

Некорректные/отсутствующие значения `[worktime]`, `[dashboard]`, `[salary]`, `[currency]` и `[services]` молча
заменяются дефолтами (не роняют приложение); отсутствие `[atlassian]`/`[llm]` отключает
соответствующие фичи целиком; отсутствие `[git]`/`[templates]`/`[docs]`/`[claude]` просто убирает
из интерфейса и текстов соответствующие куски.

Перечисления (`[github].reviewers`, `[git].rebase_targets`, `[templates].review_skip_migration_repos`)
разбираются одним приватным хелпером `Config::commaList()` — формат «через запятую» у всех
списков в конфиге одинаковый, новый список добавляй через него же, а не своим `explode()`.

## Бизнес-правила чек-листа

- **Ссылка на задачу валидируется до создания записи в БД** — сначала формат
  (`TaskRepository::parseTaskId`, ключ вида `PROJ-123`), затем реальное существование задачи
  в Jira (`TaskService::assertIssueExistsInJira`, только для новых задач). Опечатка в ключе или
  случайная ссылка не заводят мусорную задачу в БД, а возвращают 422 с текстом ошибки.
  **Недоступность Jira валидацией не считается** (сеть, 5xx, 401/403 — задача создаётся как
  раньше): это best-effort по тому же принципу, что и `syncJira()`, иначе при упавшей Jira
  приложением нельзя было бы пользоваться. Единственный ответ Jira, который блокирует создание,
  — HTTP 404 на саму задачу.
- **Новая задача** (ссылка не найдена в БД) — чек-лист создаётся полностью пустым (все
  пункты не отмечены).
- **Режим Claude Code Skill — флаг конкретной задачи, не общий конфиг** (`tasks.claude_code_skill_mode`,
  по умолчанию `1` у каждой новой задачи; переключается в настройках приложения, раздел «Эта
  задача», видимый только пока задача открыта — `api/toggle_claude_code_skill_mode.php` →
  `TaskRepository::updateClaudeCodeSkillMode()`). Раньше это была общая настройка
  `[mode].claude_code_skill_mode` в `config/params.ini` — теперь у каждой задачи своё значение,
  и часть задач можно вести через скилл, а часть — вручную, не переключая ничего глобально.
  Пока флаг включён, пункты из `ChecklistRepository::CLAUDE_CODE_SKILL_MODE_HIDDEN_CODES`
  (сейчас `code_written`, `pull_request`, `claude_review`, `pr_description` — эти шаги делает
  скилл Claude Code) не попадают в ответ ни одного эндпоинта: фильтр — прямо в SQL
  `getStatusesForTask()` по `t.claude_code_skill_mode` из уже присоединённой туда же таблицы
  `tasks` (рядом с `HIDE_IF_STORY_POINTS_ALREADY_SET_CODE`), поэтому они не показываются, не
  участвуют в прогрессе и в очерёдности шагов. **Отметки в `task_checklist` остаются в БД** —
  выключение флага у задачи возвращает пункты вместе с уже проставленными галочками. Обратная
  сторона того же фильтра — `CLAUDE_CODE_SKILL_MODE_ONLY_CODES` (сейчас `skill_commit`): эти
  пункты существуют только пока флаг включён, при выключенном скрываются тем же условием.
  Именно поэтому пункты **не удалены** из
  `Database::CHECKLIST_ITEMS`: удаление оттуда стирает и сам пункт, и все галочки задач
  (`pruneRemovedItems`), то есть было бы необратимо. Поскольку значение читается из той же
  строки `tasks`, что уже присоединена в запросе, `ChecklistRepository` про этот режим ничего
  не спрашивает у `Config` — фильтр целиком в SQL, никакого отдельного параметра метода
  `getStatusesForTask()` для этого не потребовалось.
  Зависимости других пунктов от скрытых проверяются на фронте через `hasChecklistItem(code)`
  (`app.js`) — по составу чек-листа из ответа API, а не вторым списком скрытых пунктов (DRY):
  так у `jira_description` пропадает кнопка «Скопировать PR». Добавляя новую зависимость между
  пунктами — проверяй наличие пункта-источника этой же функцией, а не считай его существующим
  всегда.
- **Повторное открытие существующей задачи НЕ сбрасывает чек-лист** — ни ручной ввод ссылки,
  ни клик по строке в «Последних задачах» (оба идут через `TaskService::findOrCreateByLink`)
  не трогают отметки, только перечитывают заголовок/описание из Jira (`syncJira()`).
  Единственное действие, которое сбрасывает чек-лист живой задачи — кнопка «Начать заново»
  (`ChecklistRepository::resetAll()`); отдельно от этого удаление задачи (`deleteByLink()`)
  стирает её полностью, а не только отметки. Логика `resetAll()`: все пункты обнуляются,
  а пункты из `ChecklistRepository::ALWAYS_DONE_ON_RESET_CODES` (сейчас пуст) принудительно
  отмечаются выполненными — это для метаданных уровня задачи, не имеющих смысла
  «переделывать» в каждом новом цикле работы. Новые пункты чек-листа по умолчанию попадают
  в «обнуляемые»; чтобы пункт вместо этого всегда становился выполненным при сбросе — его
  `code` нужно явно добавить в эту константу. `story_points` раньше был в этой константе, но
  убран: с появлением скрытия пункта по реальному статусу в Jira (см. ниже) форсировать его
  `is_done` при сбросе было бы неверно — пункт остался бы скрытым как «выполненный», даже
  если Story Points в Jira ещё не проставлен. Теперь при сбросе он ведёт себя как все
  остальные пункты (обнуляется), а показывать/скрывать его — задача отдельного правила.
- **Выполненные пункты не отображаются в списке** — после отметки пункт галочкой остаётся
  видимым ~0.5с, затем плавно анимированно скрывается (`animateItemCompletion` в `app.js`) и
  больше не рендерится, пока не будет сброшен.
- **Пункты выполняются строго по очереди** — из невыполненных активен и доступен для клика
  только первый (по `sort_order`), остальные заблокированы (класс `.locked`: приглушены,
  клик игнорируется). Как только активный пункт улетает по анимации, следующий автоматически
  разблокируется (`updateLockState()` в `app.js`, вызывается и при полном рендере, и сразу
  после удаления улетевшего пункта из DOM). Клик-обработчик у `li` также проверяет класс
  `.done` (не только `.locked`) — пункт остаётся кликабельным ~0.5с до улёта, а замыкание
  держит устаревший объект `item` (`state.checklist` к этому моменту уже заменён новым
  массивом из ответа API), поэтому проверка `item.is_done` внутри обработчика не спасает —
  нужна проверка по классу самого DOM-элемента. **Исключение из строгой очерёдности** — кнопка
  «Перейти сюда» (`.jump-here-btn`, есть у каждого видимого пункта) → `jumpToItem()` в `app.js`:
  массово отмечает выполненными все пункты выше выбранного напрямую через `api/toggle.php`
  (`is_done: true`), **без вызова их реальных обработчиков** — побочные эффекты пункта (ветка,
  ссылка на PR, переход статуса в Jira и т.п.) при этом не выполняются и не сохраняются, пункт
  просто пропускается. Осознанный «эскейп-люк» на случай, когда шаг уже сделан вручную вне
  приложения — не расширяй его на обработчик самого пункта.
- **Прогресс-бар** — процент `is_done` от общего числа пунктов данной задачи, пересчитывается
  при каждом изменении состояния.
- **Пункт «Указать Story Points» показывается только если в задаче Jira Story Points
  действительно не проставлен.** Флаг `tasks.story_points_set` обновляется при каждой
  синхронизации (`JiraSyncService::sync()` → `JiraClient::fetchIssue()` читает кастомное поле
  Story Points, `Config::atlassianStoryPointsField()`), так же как заголовок/описание.
  Фильтрация — на уровне SQL в `ChecklistRepository::getStatusesForTask()`
  (`HIDE_IF_STORY_POINTS_ALREADY_SET_CODE`), а не на фронте: пункт полностью выпадает из
  ответа API для всех эндпоинтов сразу, без дублирования правила в каждом месте, где читается
  чек-лист.
- **Достижение дневной нормы часов → модалка поздравления.** Не пункт чек-листа, а побочный
  эффект успешного трека времени: `showCongratsModal()` (`app.js`) вызывается из
  `openQuickTrackModal()` сразу после успешной отправки worklog в Jira, если норма
  `[worktime].daily_hours` достигнута **впервые за сегодня** —
  `alreadySeconds < normSeconds && totalSecondsToday >= normSeconds`, где `alreadySeconds` — то,
  что было затрекано до этого конкретного трека. Условие чисто арифметическое, без
  сохранения где-либо факта «уже показывали сегодня» — сверхурочный трек после того, как норма
  уже была выполнена ранее в тот же день, модалку не повторяет. Срабатывает из обеих точек
  входа в `openQuickTrackModal()` — кружка быстрого трека и пункта `time_tracking`.
  Модалка параллельно и независимо (`Promise.all`, у каждого запроса свой `.catch(() => null)`)
  подгружает: заработок за отработанные сегодня секунды (`api/calc_earnings.php` →
  `EarningsService`, строка «Ты заработал сегодня +N <валюта> 💸» не показывается, если запрос не
  удался или сумма ⩽ 0) и мотивационную цитату (`api/generate_motivation_quote.php` →
  `MotivationQuoteService` — реальная случайная цитата из открытого API, переведённая на
  русский; показывается вместе с именем автора, при ошибке — случайная из локального
  фолбэк-массива `MOTIVATION_QUOTES_FALLBACK`, 5 фраз в `app.js`, уже без автора, чтобы модалка
  не зависела от внешней сети) и список сегодняшних задач с затреканным временем
  (`api/today_time_spent_breakdown.php`, блок `.congrats-tasks`: заголовок «Задачи за сегодня:
  N · Ч ч М м» — количество задач и сумма времени, посчитанная по самой разбивке, а не по
  переданным в модалку секундам, чтобы итог всегда сходился с показанным списком; ниже строки
  «ключ задачи (ссылка на Jira) + тайтл + время», при ошибке запроса или пустом списке блок не
  показывается). Разметка строк списка — общая с модалкой иконки-задач и модалками
  показателей дашборда (`taskListHtml()` в `app.js`, в поздравлении вызывается с
  `withStatus: false` — статус Jira там не нужен и не влезает).
  Ошибка одного из трёх запросов не блокирует показ модалки и не прячет результаты остальных.
  Единственная кнопка — «Отдыхать». Индикация загрузки — третий способ из раздела ниже
  (`showGlobalLoader()`/`hideGlobalLoader()` вокруг `Promise.all`): к моменту вызова кнопка
  «Затрекать» уже закрыла модалку и свою собственную индикацию через `setButtonLoading`, так
  что спиннер показать не на чем — тот же случай, что у `deleteRecentTask()`/`restoreTask()`.

модалки; «Отмена» и финальная кнопка(и) — в нижней панели действий (`.modal-actions`, порядок
описан в стандарте по числу кнопок ниже). Группа `.modal-copy-actions` есть у `git_branch`
(«Сгенерировать» / «Скопировать»), `skill_commit` («Скопировать /commit», затем «Сгенерировать» и отдельная «Скопировать»
после генерации), `code_written`
(«Сгенерировать Description»),
`claude_review` («Скопировать»), `pr_description` («Сгенерировать», затем отдельная
«Скопировать» после генерации) и `jira_description` («Скопировать» / «Скопировать PR»).
Без отдельной группы
копирования — `story_points` (модалка с radio-выбором, без копирования) и `pull_request`
(своя кнопка копирования команды внутри разметки шагов `.pr-steps`, не через
`.modal-copy-actions`).

Модалки с большим многострочным вводом (`code_written`, `pr_description`, `skill_commit`)
раскрываются во весь
экран страницы вместо карточки 360px — обёртка `.form-modal` в теле модалки, вся вёрстка в CSS
через `.modal:has(.form-modal)` (тот же приём `:has()`, что у `.worktime` и `.today-tasks-modal`).
Добавляя новую модалку, где текстовое поле должно занимать всё окно, — оборачивай тело в
`.form-modal`, а поле помечай `data-description`/`data-instruction`, не пиши для неё свои
CSS-правила.

**Стандарт для панели действий (`.modal-actions`) по числу кнопок — обязателен при добавлении
новых модалок:**
- **2 кнопки** («Отмена» + финальная, либо любая другая пара) — горизонтальный ряд,
  `justify-content: space-between`, первая кнопка слева, вторая справа. Это единственный
  случай, где горизонтальное расположение допустимо.
- **3+ кнопки** (например «Отмена» / «Оставить текущую» / «Сохранить» у `git_branch`) —
  горизонтальный ряд на ширине
  500×500 **не помещается** и рвётся неровно (часть кнопок переносится на свою строку, часть
  остаётся в предыдущей — визуально хаотично). Обязателен вертикальный full-width стек:
  `.modal-actions--stacked` (`flex-direction: column`, каждая кнопка `width: 100%`), порядок
  кнопок сохраняется как передан в `buttons` (Отмена — первая/верхняя, финальная кнопка —
  последняя/нижняя). Класс переключается автоматически в `showModal()` по `buttons.length > 2` —
  при добавлении новой модалки с 3+ кнопками ничего дополнительно делать не нужно, просто не
  нарушай этот автоматизм ручной вёрсткой кнопок.
- Кнопки копирования в `.modal-copy-actions` в это правило не входят — это отдельная зона
  сверху тела модалки, а не часть `.modal-actions`.

**Индикация загрузки — обязательна для любого запроса к внешнему сервису (Jira, Git,
нейронка и т.п.) или для любого другого действия, которое очевидно выполняется не мгновенно.**
Запросы к собственному `api/*.php`, которые внутри не ходят во внешний сервис (например
`toggle.php`, `finish.php` — просто читают/пишут SQLite), быстрые и в индикации не нуждаются.

**Стиль — единый на всё приложение, минималистичный, в духе macOS Tahoe / iOS (Liquid Glass).**
Ориентир — Apple Human Interface Guidelines, раздел Progress Indicators
(https://developer.apple.com/design/human-interface-guidelines/components/status/progress-indicators/):
activity-индикатор должен быть маленьким и незаметным, показываться **рядом с конкретным
контролом**, а не поверх результата его работы (то есть не на месте, где появится финальная
галочка/иконка); крутиться непрерывно без остановок; никогда не подписывается текстом;
никогда не переходит в вид прогресс-бара. Отсюда — единственный спиннер на всё приложение,
`.ios-spinner` (`style.css`) — 8 затухающих по кругу «спиц» (воспроизводит системный
`UIActivityIndicatorView`), а не грубое кольцо с одним светлым сегментом. Разметка — через
`spinnerHtml()`/`spinnerHtml('lg')` в `app.js`, цвет — `currentColor` (наследуется от
родителя). **Новый индикатор загрузки — всегда через один из четырёх способов ниже; не
изобретай свой вид спиннера или своё расположение.**

Первые три варианта — про то, что запускает запрос (спиннер рядом с контролом), четвёртый —
про место, где данные появятся:
- **Кнопка, которая остаётся видимой на время запроса** (кнопка внутри модалки с `keepOpen`,
  либо кнопка со своим `addEventListener` вроде «Сгенерировать»/«Сгенерировать Description») —
  `setButtonLoading(buttonEl, true/false)` в `app.js`: вставляет/убирает `.ios-spinner` внутрь
  кнопки, гасит текст (`.btn-loading` делает `color: transparent`), ставит `disabled`. Не
  дублируй этот паттерн руками — всегда через хелпер. Пример — `story_points`, `log_time`,
  `generate_branch_name`, `generate_commit_message`, кнопка «Открыть» на экране ввода ссылки.
  Особый случай — строка «Последних задач»: класс `.btn-loading` там используется только как
  хук для показа волновой анимации `.task-ripple` (эффект касания воды), без `.ios-spinner`, —
  осознанное исключение, задокументированное прямо в CSS, руками не трогать и не унифицировать.
- **Пункт чек-листа, который делает запрос прямо по клику, без модалки** (например
  `status_pull_request`, а также первичная подгрузка данных в `time_tracking` до открытия
  модалки) — `setItemLoading(checklistId, true/false)` в `app.js`, класс `.loading` на `<li>`.
  По правилу HIG выше спиннер **не** показывается на чекбоксе (там появится финальная
  галочка) — он показывается в слоте иконки сервиса справа (`.item-spinner`, временно
  подменяет `.service-icon`), чекбокс и заголовок на это время просто приглушаются. Пункт
  временно не кликается (`pointer-events: none` из CSS + проверка класса `loading` в
  клик-хендлере рядом с `locked`/`done`).
- **Кнопка, которая уже закрыла модалку** (обычная кнопка `buttons` без `keepOpen`/`getValue`,
  после которой код делает запрос к внешнему сервису) — на самой кнопке спиннер показать
  нельзя, она уже не в DOM. Показывается глобальный прелоадер по центру экрана:
  `showGlobalLoader()` вызывается **после** того как модалка закрылась и **непосредственно
  перед** запросом, `hideGlobalLoader()` — в `finally`. Пример — `deleteRecentTask()` (кнопка
  «Удалить» в модалке подтверждения закрывается сразу, `api/delete_task.php` уходит уже после).
  Тот же приём — для запроса, который стартует ещё до появления любого экрана: восстановление
  задачи при загрузке страницы (`restoreTask()` дёргает Jira через `refresh_jira`, пока оба
  экрана скрыты).
- **Место, где появятся данные, пока пустое** (значение подгружается само, без нажатия кнопки:
  показатель дашборда, индикатор затреканного времени, процент выполнения в строке «Последних
  задач») — **скелетон**, а не спиннер: `skeletonHtml()` в `app.js` вставляет
  `<span class="skeleton">` — плашку с бегущим бликом ровно на месте будущего значения
  (`.skeleton` + `@keyframes skeleton-shimmer` в `style.css`). Спиннер здесь запрещён тем же
  правилом HIG (он рядом с контролом, а не на месте результата), а пустое место читается как
  «сломалось». Правила скелетона:
  - **один класс на всё приложение**, цвет — `currentColor` (плашка сама выходит в цвет
    значения, которое в ней появится), размер — переменные `--skeleton-w`/`--skeleton-h` в
    правиле места применения (`.metric-value .skeleton`, `.recent-task-percent .skeleton`,
    `.today-time #today-time-value .skeleton`), а не инлайн-стилями и не новыми классами;
  - **слот значения должен держать свой размер** (`min-width`/`min-height` у контейнера) —
    иначе появление данных сдвинет вёрстку, и весь смысл скелетона теряется;
  - плашка не обещает больше, чем придёт: ширина примерно как у настоящего значения;
  - скелетон **не отменяет спиннер там, где есть контрол** — у дашборда одновременно скелетон
    в плитке и `setButtonLoading` на кнопке актуализации;
  - ошибка запроса — скелетон убирается (пустое значение или скрытый блок), он не должен
    крутиться вечно.

Добавляя новый пункт/действие с сетевым запросом к внешнему сервису — выбери из четырёх
вариантов выше по тому, что запускает запрос и где появится результат, а не изобретай новый
способ индикации. Появилось новое место, куда данные подгружаются в фоне — там скелетон
нужен по умолчанию, отдельной просьбы для этого не требуется.

**Подсказки при наведении — только собственный тултип, нативный `title` запрещён.** Нативный
`title` не стилизуется, всплывает с системной задержкой, рисуется системным шрифтом мимо темы
приложения и выбивается из общего вида. Вместо него — атрибут `data-tooltip="текст"` на любом
элементе; показ берёт на себя единый делегат в `app.js` (`showTooltip()`/`hideTooltip()`,
слушатели `mouseover`/`mouseout`/`click` на `document`), а вид — единственный элемент
`#tooltip` (`.tooltip` в `style.css`, стеклянная плашка в духе macOS Tahoe с мягким
появлением). Правила, которые нельзя нарушать при добавлении новых подсказок:
- **никаких `title=` в разметке и `el.title = ...` в JS** — только `data-tooltip` (для
  доступности рядом ставится `aria-label`, если у элемента нет текстовой подписи);
- **не создавай второй вид тултипа** — ни своей плашки, ни своего позиционирования; всё через
  `data-tooltip`, в том числе у динамически отрисованных элементов (делегирование на `document`
  ловит их автоматически, вешать обработчики на каждый элемент не нужно);
- **динамический текст** (например «обновлено 4 мин назад») — обновляй `el.dataset.tooltip`
  на `mouseenter` элемента: делегат читает текст в момент показа, а не наведения;
- позиционирование — под элементом, а при нехватке места снизу автоматически над ним (окно
  всего 500×500, поэтому переворот обязателен и уже реализован в `positionTooltip()`).

Вся таблица «поведение» реализована как карта `ITEM_HANDLERS` в `public/assets/js/app.js` —
при изменении поведения пункта правь соответствующую запись там же. Колонка «Сервис» —
чисто визуальная (иконка справа в строке + лёгкая подсветка фона в цвет сервиса), задаётся
отдельной картой `ITEM_SERVICE` там же и не хранится в БД (это не бизнес-данные, а
презентационная привязка «какой сервис нужен для этого шага»). Меняя/добавляя пункт в
`Database::CHECKLIST_ITEMS` — не забудь добавить его `code` и в `ITEM_HANDLERS`, и в
`ITEM_SERVICE` на фронте, иначе пункт останется без обработчика клика и без иконки.

## API

Все эндпоинты — `POST`, JSON-in/JSON-out, эндпоинт для БД — весь `App\*` через
`api/_bootstrap.php` (автозагрузка, `Database::connection()`, хелперы `readJsonInput()`/`respond()`,
проверка источника запроса `assertSameOrigin()` — см. «Безопасность»; 403, если запрос пришёл не
со страницы приложения).

### `POST /api/task.php` — найти или создать задачу

Запрос: `{ "link": "https://.../browse/PROJ-123" }`

Логика (`TaskService::findOrCreateByLink`):
- строго извлекает `task_id` из ссылки (`TaskRepository::parseTaskId`: `/browse/XXX-1`, просто
  `"XXX-1"`, либо ключ как отдельный токен в любом месте URL — так открываются ссылки вида
  `?selectedIssue=XXX-1`). Ключ не найден — **422**, задача не создаётся;
- ищет задачу по `task_link` или `task_id`;
- если найдена — возвращает её текущий чек-лист как есть, без сброса и без проверки в Jira
  (задача уже открывалась, значит валидна);
- если не найдена — сначала проверяет, что задача реально существует в Jira
  (`JiraSyncService::issueExists` → `JiraClient::issueExists`, HTTP 404 = нет такой задачи),
  и только потом создаёт запись и пустой чек-лист. Задачи нет в Jira — **422**, в БД ничего
  не пишется.

В обоих случаях перечитывает заголовок/описание из Jira (`syncJira()`).

Ответ: `{ "task": {...}, "checklist": [{id, code, title, is_done}, ...], "isNew": bool }`;
**422** с текстом ошибки в `error` — единственный код ошибки эндпоинта, оба случая выше
(нераспознанная ссылка и отсутствующая в Jira задача) это ошибка ввода. Фронт показывает текст
под полем ввода (`linkError` в `loadTask()`).

Вызывается когда пользователь вводит ссылку на экране ввода или кликает по строке в
«Последних задачах» (`loadTask()` в `app.js`) — в обоих случаях чек-лист не сбрасывается,
только подтягиваются свежие данные из Jira.

### `POST /api/state.php` — прочитать текущее состояние задачи (без побочных эффектов)

Запрос: `{ "link": "https://.../browse/PROJ-123" }`

Только ищет задачу и отдаёт её текущий чек-лист как есть, ничего не создаёт. 404
(`{"error": "Задача не найдена"}`), если задачи с такой ссылкой/id нет.

Ответ: `{ "task": {...}, "checklist": [...] }`

Вызывается при восстановлении последней открытой задачи из `localStorage` после обновления
страницы (`restoreTask()` в `app.js`, с `refresh_jira: true`) и при подгрузке процента
выполнения для строк «Последних задачи» (без `refresh_jira` — там это лёгкий предпросмотр, не
открытие). В отличие от `task.php` не умеет создавать задачу — если задачи нет, это 404,
а не повод её завести.

### `POST /api/toggle.php` — отметить пункт чек-листа

Запрос: `{ "task_id": 1, "checklist_id": 3, "done": true, "branch": "feature/..." (опционально) }`

`branch` используется только пунктом `git_branch` — если передан непустым, обновляет
`tasks.git_branch` до отметки пункта.

Ответ: `{ "task": {...}, "checklist": [...] }`

### `POST /api/toggle_claude_code_skill_mode.php` — переключить режим Claude Code Skill у задачи

Запрос: `{ "task_id": 1, "enabled": true }`

Логика: `TaskRepository::updateClaudeCodeSkillMode()` пишет флаг прямо в `tasks.claude_code_skill_mode`
этой задачи и перечитывает её чек-лист — никакой бизнес-логики сверх записи в БД нет, поэтому
`TaskService` не нужен (тот же случай, что у `api/toggle.php`, — репозитории напрямую). 422 —
не передан `task_id`. Пункты, которые появляются/пропадают при переключении — см. бизнес-правило
«Режим Claude Code Skill» выше.

Ответ: `{ "task": {...}, "checklist": [...] }`

Вызывается по переключению тумблера «Claude Code Skill» в разделе «Эта задача» настроек —
без модалки, эндпоинт не ходит во внешний сервис (пишет только SQLite), поэтому без индикации
загрузки (тот же паттерн, что у `api/toggle_claude_notifications.php`); при ошибке фронт
откатывает тумблер визуально и показывает тост с текстом ошибки.

### `POST /api/finish.php` — «Завершить задачу»

Запрос: `{ "task_id": 1 }`

Сбрасывает чек-лист (`ChecklistRepository::resetAll`) — см. «Сброс чек-листа» в бизнес-правилах:
все пункты обнуляются, кроме `ALWAYS_DONE_ON_RESET_CODES` (принудительно отмечаются выполненными).

Ответ: `{ "checklist": [...] }`

### `POST /api/delete_task.php` — удалить задачу

Запрос: `{ "link": "https://.../browse/PROJ-123" }`

Полностью удаляет задачу и её чек-лист из БД (`TaskService::deleteByLink` →
`ChecklistRepository::deleteForTask` + `TaskRepository::delete`) — без возврата, в отличие от
`finish.php`, который только сбрасывает отметки. 404 (`{"error": "Задача не найдена"}`), если
задачи с такой ссылкой/id нет.

Вызывается из списка «Последние задачи» на экране ввода ссылки (иконка корзины у строки,
`app.js`) — после подтверждения в модалке удаляет запись и из `devflow_recent_tasks` в
`localStorage`.

Ответ: `{ "success": true }`

### `POST /api/dashboard.php` — показатели дашборда

Запрос: `{}` (без параметров)

Read-only (`DashboardService::metrics()`): считает числовые показатели дашборда на экране ввода
ссылки. Сейчас показатель один — задачи, зависшие в статусе Pull request
(`atlassian.pull_request_status`) дольше `[dashboard].stale_pull_request_hours` (по умолчанию 24 ч):
`JiraClient::fetchIssuesStuckInStatus()` ищет их JQL-запросом
`assignee = currentUser() AND status = "…" AND status CHANGED TO "…" BEFORE "<дата-порог>"`
(через тот же `/rest/api/2/search/jql`, что и сегодняшние ворклоги; выборка ограничена 100 задачами).
**Момент попадания в статус берётся из истории изменений**, а не из `updated`
(его меняет любой комментарий) и не из `statuscategorychangedate` (у Doing и Pull request одна
категория, дата не обновляется). Сам JQL (`status CHANGED TO ... BEFORE ...`) проверяет лишь
факт когда-либо случившегося перехода до даты-порога, поэтому нашедшихся кандидатов
`JiraClient::fetchIssuesStuckInStatus()` дополнительно фильтрует по changelog
(`lastTransitionToStatus()`): задача, успевшая выйти из статуса и вернуться в него уже после
даты-порога, в показатель не попадает — учитывается именно последний переход, а не любой.
Дозапрос идёт только по уже отфильтрованным JQL кандидатам (их единицы), а не по всем задачам
пользователя. 422 — интеграция с Jira не настроена; 502 — ошибка Jira.

**Нерабочие дни в счёт часов «зависания» не идут** (`[worktime].non_working_days`, по умолчанию
сб и вс): перевели PR в пятницу 17:00 — при пороге 24 ч он станет зависшим только в
понедельник 17:00, а не в субботу. Поэтому в JQL уходит **абсолютный** момент-порог
(`"yyyy/MM/dd HH:mm"`), а не относительное `-24h`, которое пропускать дни не умеет:
`DashboardService::staleCutoff()` отсчитывает порог назад по одному часу, не убавляя счётчик
на нерабочих днях. Дата в JQL трактуется в таймзоне пользователя Jira, поэтому «сейчас» берётся
в ней же (`JiraSyncService::getUserTimeZone()` → `JiraClient::fetchUserTimeZone()`, `/myself`) —
контейнер живёт в UTC и давал бы сдвиг. `Config::nonWorkingWeekdays()` не отдаёт все семь дней
разом (иначе отсчёт порога не сошёлся бы никогда).

Ответ: `{ "stale_pull_requests": { "count": 3, "hours": 24, "status": "Pull request",
"non_working_weekdays": [6, 7],
"tasks": [{ "task_id": "PROJ-123", "title": "…", "status": "Pull request", "link": "https://…" }] } }`

Число и список приходят одним ответом — по клику на показатель список задач берётся из уже
полученных данных, второго запроса к Jira нет. Название статуса, порог и нерабочие дни
(`non_working_weekdays`, номера ISO-8601) тоже приходят с сервера: подпись, подсказка показателя
и приписка «(Сб, Вс не считаем)» собираются из них, на фронте не зашиты.

Вызывается из `loadDashboard()` в `app.js` — при инициализации (независимо от загрузки задачи,
как `loadTodayTimeSpent()`), по кнопке актуализации в блоке дашборда и при возврате фокуса к окну
(`refreshDashboardOnReturn()`, не чаще раза в `BACKGROUND_REFRESH_MS` = 60 с — PR ревьювят и
мерджат в другой вкладке, поэтому к возвращению показатели уже устарели). Периодического опроса
по таймеру нет — как и у индикатора затреканного времени, с которым дашборд делит и константу
троттлинга, и общий обработчик возврата фокуса (`refreshOnReturn()` в инициализации).

### `POST /api/today_time_spent.php` — затреканное сегодня время (по всем задачам)

Запрос: `{ "task_id": 1 }` — `task_id` (`tasks.id`) необязателен, см. правило про задержку
индекса Jira ниже.

Read-only: считает суммарное время ворклогов текущего пользователя Jira за сегодня по всем
задачам (`TaskService::getTodayTimeSpentSeconds` → `JiraSyncService` →
`JiraClient::fetchTodayTimeSpentSeconds`):
JQL-поиск `worklogAuthor = currentUser() AND worklogDate >= startOfDay()` → ворклоги каждой
найденной задачи → суммируются только свои и только попавшие в границы текущих суток.
«Сегодня» считается в таймзоне пользователя Jira (`/myself` → `timeZone`), а не сервера —
контейнер живёт в UTC и на границах суток давал бы сдвиг. 422, если интеграция с Jira не
настроена; 502 при ошибке Jira. **Поиск идёт через `/rest/api/2/search/jql`** — старый
`/rest/api/2/search` на Jira Cloud удалён и отвечает HTTP 410, не возвращай его.

**Индекс JQL-поиска на Jira Cloud обновляется с задержкой** — только что добавленный worklog
в выборку не попадает, поэтому сразу после трека задача (а у первого за день трека — и весь
результат) оказывалась пустой. Отсюда необязательный `task_id`: задачу с этим `tasks.id`
`JiraClient` читает напрямую по ключу (`/issue/<key>?fields=summary,status`) и добавляет к
найденным поиском, если поиск её не вернул. Дозапрос — best-effort: задачи может не быть в
Jira, тогда ошибка глотается и отдаётся то, что нашёл поиск. Фронт передаёт открытую задачу
всегда, когда она есть (`ensureTaskPayload()` в `app.js`) — во всех вызовах обоих эндпоинтов
сегодняшнего времени.

Ответ: `{ "time_spent_seconds": 1200 }`

Вызывается из `loadTodayTimeSpent()` в `app.js` — при инициализации (намеренно вне цепочки
загрузки задачи: индикатор появляется сам, когда Jira ответит, и ничего не задерживает),
после успешного трека времени в пункте `time_tracking`, при возврате фокуса к окну
(`refreshTodayTimeSpentOnReturn()` на `visibilitychange` + `focus`, не чаще раза в
`BACKGROUND_REFRESH_MS` = 60 с — так учитывается время, затреканное руками прямо в Jira;
слушатели `visibilitychange`/`focus` навешаны один раз в инициализации и дёргают заодно
показатели дашборда, у каждого свой троттлинг),
по клику на сам индикатор (клик — явный запрос пользователя, поэтому идёт мимо троттлинга) и
перед открытием модалки быстрого трека времени (см. ниже — от этого числа считаются и
подсветка относительно нормы, и объём добавляемого времени). Периодического опроса по таймеру
нет и не нужно.

### `POST /api/today_time_spent_breakdown.php` — сегодняшнее время по задачам (список)

Запрос: `{ "task_id": 1 }` — `task_id` (`tasks.id`) необязателен, тот же смысл и та же причина
(задержка индекса JQL), что у `today_time_spent.php`.

Read-only (`TaskService::getTodayTimeSpentBreakdown` → `JiraSyncService` →
`JiraClient::fetchTodayTimeSpentBreakdown`):
та же выборка задач и ворклогов, что у `today_time_spent.php`, но без суммирования в одно
число — по каждой задаче с ненулевым сегодняшним временем возвращается `task_id`, `title` и
`status` (вместе с `key` дозапрашиваются `summary`/`status` в том же JQL-поиске), `link`
(собирается из `atlassian.base_url` + `/browse/<key>`) и `seconds`. 422/502 — та же схема, что
у `today_time_spent.php`.

Ответ: `{ "tasks": [{ "task_id": "PROJ-123", "title": "...", "status": "In Progress", "link": "https://.../browse/PROJ-123", "seconds": 1200 }, ...] }`

Вызывается по клику на иконку `#today-tasks-btn` (третий кружок в `.today-time-group`,
всплывает по наведению рядом с кружком быстрого трека) — модалка со списком задач, каждая
строка кликабельна и ведёт на задачу в Jira в новой вкладке.

### `POST /api/get_time_spent.php` — уже затреканное время по одной задаче (read-only)

Запрос: `{ "task_id": 1 }`

Read-only (`TaskService::getTimeSpentSeconds` → `JiraSyncService::getTimeSpentSeconds` →
`JiraClient::fetchTimeSpentSeconds`): в отличие от `today_time_spent.php` не по всем задачам
пользователя, а по одной конкретной, и требует `task_id`. 422, если не передан `task_id`; 502 —
задача не найдена в БД, интеграция с Jira не настроена, либо ошибка самой Jira (все три случая
неразличимы по коду ответа, различается только текст `error`).

Ответ: `{ "time_spent_seconds": 1200 }`

Вызывается из обработчика `time_tracking` в `ITEM_HANDLERS` параллельно с
`today_time_spent.php` (`Promise.all`) перед открытием модалки трека времени — оба числа нужны
сразу: одно для позиции ползунка (за сегодня по всем задачам), другое для строки «Уже
затрекано в задачу: …» над ним.

### `POST /api/log_time_quick.php` — быстрый трек времени в текущую задачу

Запрос: `{ "task_id": 1, "minutes": 95 }`

Добавляет worklog в Jira (`TaskService::logTimeOnly` → `JiraSyncService::addWorklog`) и
**не трогает чек-лист** — в отличие от `log_time.php`, где трек времени является выполнением
пункта `time_tracking`. Обе операции идут через один и тот же `logTimeOnly()`, `logTime()`
лишь добавляет к нему отметку пункта. 422 при пустой задаче/нулевом времени, 502 при ошибке Jira.

Ответ: `{ "success": true }`

Вызывается из модалки быстрого трека времени (`openQuickTrackModal()` в `app.js`), после
успеха фронт перезапрашивает индикатор через `loadTodayTimeSpent()`.

### `POST /api/log_time.php` — затрекать время и отметить пункт чек-листа

Запрос: `{ "task_id": 1, "checklist_id": 3, "hours": 1, "minutes": 35 }`

`hours`/`minutes` складываются в секунды (`hours*3600 + minutes*60`). Логика
(`TaskService::logTime` → `logTimeOnly` → `JiraSyncService::addWorklog`) переиспользует тот же
`logTimeOnly()`, что и `log_time_quick.php`, и дополнительно отмечает пункт чек-листа
выполненным — **только при успешном ответе Jira** (в отличие от `log_time_quick.php`, который
чек-лист вообще не трогает). 422 — не переданы `task_id`/`checklist_id` либо итоговое время
⩽ 0; 502 — задача не найдена / интеграция с Jira не настроена / ошибка Jira.

Ответ: `{ "task": {...}, "checklist": [...] }`

Вызывается как `submit` внутри `openQuickTrackModal()` из обработчика пункта `time_tracking` —
единственное отличие от кружка быстрого трека (который вызывает `log_time_quick.php`) в этом
и есть: свой эндпоинт + своя отметка пункта.

### `POST /api/update_story_points.php` — проставить Story Points в Jira

Запрос: `{ "task_id": 1, "checklist_id": 3, "story_points": 5 }`

Логика (`TaskService::updateStoryPoints`): требует настроенную интеграцию с Jira → проставляет
Story Points в самой задаче Jira (`JiraSyncService::updateStoryPoints` → `JiraClient`,
кастомное поле — `Config::atlassianStoryPointsField()`) → отмечает пункт чек-листа выполненным
— только при успешном ответе Jira (тот же паттерн, что у `transition_doing.php`/
`transition_pull_request.php` ниже). 422 — не переданы `task_id`/`checklist_id`/`story_points`
(или `story_points ⩽ 0`); 502 — задача не найдена / интеграция с Jira не настроена / ошибка Jira
(неразличимо по коду ответа, только по тексту `error`).

Ответ: `{ "task": {...}, "checklist": [...] }`

Вызывается из обработчика `story_points` в `ITEM_HANDLERS` — кнопка «Подтвердить» в модалке
выбора значения (`keepOpen`, спиннер через `setButtonLoading`, модалка закрывается вручную
только при успехе).

### `POST /api/transition_doing.php` — перевести задачу в Jira в статус Doing

Запрос: `{ "task_id": 1, "checklist_id": 3 }`

Логика (`TaskService::transitionToDoing`): требует настроенную интеграцию с Jira → переводит
задачу в статус из `config/params.ini` (`atlassian.doing_status`, по умолчанию «Doing») через
`JiraClient::transitionToDoing` → отмечает пункт чек-листа выполненным только при успехе.
422/502 — та же схема, что у `update_story_points.php`.

Ответ: `{ "task": {...}, "checklist": [...] }`

Вызывается из обработчика `status_doing` в `ITEM_HANDLERS` — без модалки, прямо по клику,
индикация через `setItemLoading(item.id, true)`.

### `POST /api/transition_pull_request.php` — перевести задачу в Jira в статус Pull Request

Запрос: `{ "task_id": 1, "checklist_id": 3 }`

Логика (`TaskService::transitionToPullRequest`): аналогично `transition_doing.php`, статус — из
`atlassian.pull_request_status` (по умолчанию «Pull request»). 422/502 — та же схема.

Ответ: `{ "task": {...}, "checklist": [...] }`

Вызывается из обработчика `status_pull_request` в `ITEM_HANDLERS` — без модалки,
`setItemLoading`.

### LLM-эндпоинты — общее для всех пяти

`generate_branch_name.php`, `generate_commit_message.php`, `generate_pr_description.php`,
`generate_deploy_instruction.php` и `generate_motivation_quote.php` устроены одинаково: берут клиента у
`LlmClientFactory::createFromConfig()` и зовут `chat()` через свой Service (см. «Один Client +
N Service» в разделе «Паттерны») — 502, если LLM не настроен или ответил ошибкой. **Про
провайдера эндпоинты не знают и `Config::llm()` сами не читают** — иначе выбор провайдера
пришлось бы дублировать в каждом. Ни один из пяти не пишет
ничего в БД напрямую. Исключение — `generate_motivation_quote.php`: там нейронка только
переводит уже полученную из внешнего API цитату, поэтому её недоступность не является ошибкой
эндпоинта (см. ниже).

### `POST /api/generate_branch_name.php` — сгенерировать имя git-ветки

Запрос: `{ "task_id": 1 }`

Логика: ищет задачу по `task_id` (`tasks.id`) → **404**, если не найдена; **422**, если у
задачи ещё нет `title` (Jira ни разу не синхронизировалась успешно — переоткрыть задачу или
проверить `config/params.ini`) → `BranchNameService::generate()` строит промпт из Jira-ключа,
заголовка и описания (описание предварительно очищается от HTML) → ответ чистится от
кавычек/бэктиков и описание в имени ветки принудительно обрезается до 5 слов без служебных
слов — подстраховка на случай, если нейронка не соблюдёт системный промпт точно. 502 — LLM не
настроен/ошибка нейронки.

Ответ: `{ "branch_name": "feature/PROJ-123-..." }`

Вызывается кнопкой «Сгенерировать» внутри модалки пункта `git_branch` — заполняет поле ввода
ветки результатом, индикация через `setButtonLoading`.

### `POST /api/generate_commit_message.php` — сгенерировать первую строку commit message

Запрос: `{ "description": "текст изменений", "task_id": "PROJ-123" }`

**Внимание — `task_id` здесь не `tasks.id`, а Jira-ключ строкой** (`state.task.task_id` на
фронте; так же и в `generate_pr_description.php`) — этот эндпоинт вообще не обращается к БД.
`task_id` необязателен (пустая строка допустима), обязателен только `description` (422 при
пустом значении).

Логика (`CommitMessageService::generate()`): собирает промпт (Jira-ключ + описание) по
стандарту команды — Conventional Commits с `#JIRA-KEY` в начале subject, описание не длиннее
80 символов — и зовёт `chat()` клиента нейронки; ответ возвращается как есть, без дополнительной
пост-обработки (в отличие от `generate_branch_name.php`). Промпт требует вернуть **ровно одну
строку** — ссылка на задачу, тело и футер сюда больше не входят, они ушли в описание PR
(`generate_pr_description.php`), поэтому ссылка на задачу этому эндпоинту и не передаётся.

Ответ: `{ "message": "#PROJ-123 feat: add filter for fraud user column" }`

Вызывается кнопкой «Сгенерировать Description» внутри модалки пункта `code_written` —
результат сразу копируется в буфер (`notifyCopied('commit message')`) и показывается в теле
модалки, генерацию можно повторять.

### `POST /api/generate_pr_description.php` — собрать описание PR

Запрос: `{ "description": "что сделано", "instruction": "сырой текст инструкции выливки",
"task_id": "PROJ-123", "task_link": "https://.../browse/PROJ-123" }`

Обязателен только `description` (422 при пустом значении); `instruction`, `task_id` и
`task_link` необязательны. `task_id` — Jira-ключ строкой, как в
`generate_commit_message.php`; к БД эндпоинт не обращается.

Логика (`PrDescriptionService::generate()`): системный промпт даёт нейронке шаблон описания PR
команды (`## What` / `## How` / `## Jira` / `## Checklist` / `## Screenshots / examples` /
`## Breaking changes`) и требует сохранить заголовки секций символ-в-символ, убрать
HTML-комментарии-подсказки, скопировать чек-лист неотмеченным, подставить в `## Jira` ровно
переданную ссылку, ничего не выдумывать и копировать код/идентификаторы символ-в-символ.
Дальше — единственное бизнес-правило сервиса: если `instruction` не пустая, к описанию через
пустую строку (`\n\n`, иначе на GitHub блок склеивается с последним абзацем описания)
дописывается результат `DeployInstructionService::generate()` (тот же
фиксированный шаблон `### ❗ **ВАЖНО** ❗` / `**Перед мерджем сделать следующее:**` /
`<инструкция>`, см. таблицу пунктов чек-листа для причины эмодзи вместо цвета); если пустая —
второго запроса к нейронке нет и блок в описание не попадает.

Ответ: `{ "description": "## What\n...\n## Breaking changes\nNone" }`

Вызывается кнопкой «Сгенерировать» внутри модалки пункта `pr_description` — результат
копируется сразу и показывается в теле модалки с отдельной кнопкой повторного копирования,
генерацию можно повторять.

### `POST /api/generate_deploy_instruction.php` — оформить инструкцию выливки

Запрос: `{ "instruction": "сырой текст инструкции выливки" }`

Единственный параметр обязателен (422 при пустом значении); к БД эндпоинт не обращается.
Логика — тот же `DeployInstructionService::generate()`, что зовёт `PrDescriptionService`
изнутри `generate_pr_description.php`, только результат отдаётся отдельным блоком, а не
дописывается к описанию PR (**новый Service тут не нужен — переиспользуется существующий**).
502 — LLM не настроен/ошибка нейронки.

Ответ: `{ "instruction": "### ❗ **ВАЖНО** ❗\n**Перед мерджем сделать следующее:**\n..." }`

Вызывается кнопкой «Сгенерировать» внутри модалки пункта `skill_commit` — пока у задачи включён
`claude_code_skill_mode`, пункт `pr_description` скрыт, а описание PR пишет скилл, и блок
инструкции выливки нужно получить отдельно, чтобы вставить его в PR руками.

### `POST /api/generate_motivation_quote.php` — случайная мотивационная цитата

Запрос: `{}` (без параметров)

Логика (`MotivationQuoteService::generate()`): цитата **не придумывается нейронкой**, а тянется
реальной из открытого API (`QuoteClient` → `[services].quotes_url`, по умолчанию
`zenquotes.io/api/random`, англоязычный — живых бесплатных русскоязычных API без ключа нет),
затем переводится на русский через клиента нейронки
(системный промпт: сохранить смысл и краткость, вернуть только перевод; результат чистится от
кавычек). Перевод — best-effort: если `[llm]` не настроена или нейронка упала, отдаётся оригинал
на английском, эндпоинт при этом не считается упавшим. 502 — только если недоступен сам сервис
цитат. **Никакого кэширования** — цитата запрашивается заново при каждом вызове (в отличие от
курса валют у `calc_earnings.php`).

Ответ: `{ "quote": "...", "author": "Robert Greene" }` (`author` может быть пустой строкой)

Вызывается только из `showCongratsModal()` (см. бизнес-правила — модалка поздравления при
достижении дневной нормы часов) вместе с `calc_earnings.php`, параллельно и независимо. Автор
показывается отдельной строкой под цитатой (`.congrats-quote-author`) — только для цитаты из
API. При ошибке фронт берёт случайную цитату из локального фолбэк-массива
`MOTIVATION_QUOTES_FALLBACK` в `app.js` (уже без автора), чтобы модалка не зависела от внешней
сети.

### `POST /api/calc_earnings.php` — заработок за отработанное время

Запрос: `{ "seconds": 28800 }` (отработанные сегодня секунды)

Логика (`EarningsService::earningsForSeconds`): `earnings = round(seconds/3600 *
hourlyRateUsd * rateFromUsd(), 2)`, где `hourlyRateUsd` — `Config::salaryHourlyRateUsd()`
(`[salary]` в `config/params.ini`), `rateFromUsd()` — курс USD → `[currency].code` с публичного
API (`[services].exchange_rate_url`) через `ExchangeRateClient` (файловый кэш
`storage/exchange_rate_cache.json` на 6 часов, при недоступности сервиса отдаётся устаревший
кэш, если он есть). Не привязан к задаче (нет `task_id`) — идёт мимо `TaskService`. 422 при
`seconds ⩽ 0`; 502 при ошибке курса валют.

Ответ: `{ "earnings": 1234.56, "currency_label": "грн" }`

Вызывается только из `showCongratsModal()` с `seconds` = сумма затреканного за сегодня после
трека; фронт форматирует через `formatMoney(earnings, currency_label)` — **подпись валюты
берётся из ответа, на фронте её не хардкодить**. Строка заработка в модалке не показывается,
если запрос не удался или вернул `0`.

### `POST /api/get_claude_settings.php` — состояние тумблера уведомлений Claude Code

Запрос: `{}` (без параметров)

Read-only (`ClaudeHooksService::isEnabled()`): читает `settings.json` Claude Code и проверяет,
есть ли там непустой ключ `hooks`. `available: false` — секция `[claude]` не заполнена в
`config/params.ini` (`createFromConfig()` вернул `null`) — раздел «Claude» на фронте не
показывается вовсе, а не показывается выключенным. 502 — файл `settings.json` существует, но
не читается или содержит невалидный JSON.

Ответ: `{ "available": true, "enabled": false }`

Вызывается при инициализации приложения (`loadClaudeSettings()` в `app.js`, рядом с
`loadDashboard()`/`loadTodayTimeSpent()`) — так раздел «Claude» и состояние тумблера готовы уже
к моменту первого открытия попапа настроек, без отдельного запроса по клику на шестерёнку.

### `POST /api/toggle_claude_notifications.php` — включить/выключить хуки Claude Code

Запрос: `{ "enabled": true }`

Логика (`ClaudeHooksService::setEnabled()`): `enabled: true` — записывает в `settings.json`
блок `hooks` из двух хуков (`Notification`, `Stop`, тексты — `notification_text`/`stop_text` из
`[claude]`), `enabled: false` — удаляет ключ `hooks` целиком, каким бы он ни был. 422 —
`[claude]` не настроена; 502 — `settings.json` не читается/не пишется (невалидный JSON, файл не
смонтирован, нет прав на запись).

Ответ: `{ "enabled": true }`

Вызывается по переключению тумблера «Уведомления» в разделе «Claude» настроек — без модалки,
эндпоинт не ходит во внешний сервис (пишет только локальный файл), поэтому без индикации
загрузки (см. правило про четыре способа индикации выше); при ошибке фронт откатывает тумблер
визуально и показывает тост с текстом ошибки.

## Frontend (`public/`)

- `index.php` — единственная страница. Генерирует версию статики `?v=<mtime файла>` для
  CSS/JS (`clearstatcache()` + `filemtime()`) и шлёт `Cache-Control: no-cache` на сам HTML —
  это осознанное решение против кэша браузера/встроенного PHP-сервера при активной разработке,
  **не убирай эти заголовки и версионирование**.
- `app.js` — один файл, IIFE, без модулей/сборки. Состояние (`state.task`, `state.checklist`)
  живёт в замыкании, а не в DOM — рендер-функции (`renderChecklist`, `renderGitBranch`,
  `renderProgress`) читают из `state` и перерисовывают DOM.
- **Плавающие кнопки верхнего ряда не должны наезжать на контент — правило на будущее.**
  Группа `.today-time-group` слева (кнопка возврата + индикатор времени + кружки трека) и
  `.icon-btn` настроек справа висят `position: fixed` (`top: 14px`, размер 30px) поверх
  карточки. Место под них резервирует верхний `padding` у `.app` (сейчас `50px` =
  `14 + 30 + 6` зазора) — **меняя `top`/размер этих кнопок, пересчитай отступ**. Второе
  условие того же правила: у `.app` вертикальное центрирование сделано через
  `margin-block: auto` у `.screen` при `overflow-y: auto`, а не `justify-content: center` —
  при центрировании контент, который выше окна (длинный список последних задач), переполнялся
  **вверх**, верхний `padding` визуально исчезал и карточка снова уезжала под кнопки; теперь
  такой контент скроллится. Полоса прокрутки `.app` намеренно скрыта
  (`scrollbar-width: none` + `::-webkit-scrollbar`) — в окне 500×500 она отнимала ~15px
  ширины карточки и рисовалась поверх неё. Любую новую плавающую кнопку в верхнем ряду
  проверяй в вьюпорте 500×500 и на коротком, и на переполненном экране.
- **Карточка экрана ввода ссылки не выше окна, лишнюю высоту забирает список последних задач.**
  `.link-screen` — `max-height: 100%`, `.link-card` — flex-колонка, где все блоки
  (`.link-card > *`) `flex: none`, кроме `.recent-tasks`; у `.recent-tasks-list` вместо
  фиксированного `max-height` — `min-height: 0` + `overflow-y: auto`, то есть его высота это
  «сколько осталось в карточке». Так при любом числе задач и низ карточки, и поле ссылки
  остаются видимыми в окне 500×500 (фиксированный `max-height: 240px` этого не давал: при
  длинном списке карточка вылезала за нижний край). Добавляя на этот экран новый блок —
  оставляй его `flex: none`, сжимаемым должен быть только список.
- Дашборд показателей (`.dashboard`, экран ввода ссылки, между заголовком и полем ссылки) —
  числовые показатели по Jira из `api/dashboard.php` (`loadDashboard()`), сейчас один: зависшие
  в статусе Pull request дольше `[dashboard].stale_pull_request_hours` рабочих часов. Порог,
  название статуса и нерабочие дни приходят с сервера — подпись, подсказка и приписка
  «(Сб, Вс не считаем)» (`daysOffNote()` + `WEEKDAY_SHORT` в `app.js`) собираются из ответа,
  в тексты не зашиты: не заданы нерабочие дни — приписки нет вообще. Плитка показателя
  кликабельна — открывает модалку со
  списком задач (строки — ссылки на Jira), разметка списка общая с модалками задач за сегодня и
  поздравления (`taskListHtml()`, флаги `withStatus`/`withTime`). Круглая кнопка справа —
  актуализация; давность обновления пересчитывается на `mouseenter` в `data-tooltip` (тот же
  приём, что у индикатора времени). Показатели перезапрашиваются и при возврате фокуса к окну —
  тем же общим обработчиком и с тем же троттлингом, что индикатор времени (см. `api/dashboard.php`). Индикация запроса — `setButtonLoading`
  на кнопке актуализации, и **только там**: до первой загрузки блок несёт класс `loading`
  (стоит в разметке `public/index.php`, снимается в `applyDashboard()`), который подменяет
  содержимое плитки скелетоном — плашки на местах значения и подписи (общий `.skeleton`,
  стоят прямо в разметке и затираются значением при первом успешном ответе). Раньше в слоте
  значения крутился спиннер, и плитка на секунду выглядела иначе, чем с данными (спиннер
  вместо цифры, подпись без порога часов); пустая плитка вместо него выглядела «сломанной»,
  пока Jira отвечает. У `.metric-value` задан
  `min-height` — пустой слот держит высоту плитки, размеры блока при загрузке и после
  совпадают. **Скелетон не отменяет правило трёх способов индикации выше** — это заполнение
  будущего содержимого, а не индикатор запроса; сам запрос по-прежнему показан спиннером на
  кнопке. Ошибка запроса
  (Jira не настроена/недоступна) просто скрывает блок целиком — показывать в нём нечего.
  **Цвет плитки задаётся одной переменной `--metric-color`** (класс `.metric--blue` в
  `style.css`): новый показатель = новый класс-цвет плюс метод в `DashboardService`, остальные
  CSS-правила общие — не копируй блок стилей под каждый показатель.
- Возврат к экрану ввода ссылки — стеклянный кружок со стрелкой (`.back-btn`,
  `#change-task-btn`) первым элементом в группе `.today-time-group` слева сверху, симметрично
  шестерёнке справа. Раньше это была текстовая ссылка «сменить задачу» под заголовком задачи
  (`.link-btn`): серый текст без границ не читался как кликабельный и занимал в окне 500×500
  отдельную строку. Показ — снятие класса `hidden` в `showTaskScreen()`/возврат его в
  `showLinkScreen()`, т.е. кнопка существует только внутри задачи. На ней же — красная точка
  (`.back-btn.has-alert::after`), если в дашборде есть показатель с ненулевым значением:
  внутри задачи сам дашборд не виден, а показатели обновляются в фоне (возврат фокуса к окну),
  поэтому иначе о зависших PR не узнать, не выйдя из задачи. Класс ставит
  `updateDashboardAlert()` из `applyDashboard()` (и снимает при ошибке запроса) — условие
  считается **по всем показателям ответа** через их `count`, поэтому новый показатель
  дашборда попадает в точку сам, без правок фронта.
- Индикатор затреканного сегодня времени (`.today-time`, левый верхний угол, симметрично
  иконке настроек) — формат «часы:минуты» (`formatClock()`), показывается на обоих экранах.
  Грузится независимо от страницы и задачи (`loadTodayTimeSpent()`, см. `api/today_time_spent.php`):
  пока идёт запрос — скелетон (`skeletonHtml()`) на месте значения, при ошибке индикатор
  просто скрывается.

  Подсказка при наведении — «Затрекано времени (обновлено 4 мин назад)», сокращённо (`formatAgo()`):
  `data-tooltip` пересчитывается на `mouseenter`, чтобы не держать фоновый таймер ради текста.
- Быстрый трек времени ползунком — кружок `.track-time-btn` правее индикатора, всплывает
  по наведению на группу `.today-time-group` (наведение считается по группе, а не по пилюле:
  иначе кружок прятался бы, пока мышь идёт к нему), но **не по наведению на кнопку возврата**
  `.back-btn` — она в той же группе, к треку времени отношения не имеет, поэтому оба селектора
  раскрытия исключают этот случай через `:hover:not(:has(.back-btn:hover))`. Класс `.available` ставит
  `updateTrackTimeAvailability()` — кружок доступен только когда открыта задача и индикатор
  времени не скрыт (скрыт = Jira недоступна, трекать всё равно некуда). Клик перечитывает
  затреканное за сегодня (спиннер на самом кружке через `setButtonLoading`) и открывает
  модалку `openQuickTrackModal()`. **Эта же модалка — единственный способ трека времени в
  приложении**: пункт чек-листа `time_tracking` открывает её же (см. таблицу пунктов выше),
  различаются только `submit` (свой эндпоинт + свой тост/отметка пункта) и `noteHtml` (строка
  над ползунком). Не заводи вторую модалку/форму ввода времени:
  - ползунок (`.worktime-range`, шаг `TRACK_STEP_MINUTES` = 10 мин) растянут на весь рабочий
    день из `config/params.ini` (`[worktime]` → `WORK_TIME` на фронте), слева/справа от него
    подписи начала и конца дня;
  - **позиция бегунка — это время, до которого отработан день**, поэтому сумма трека за день =
    отработанные минуты до позиции (`workedMinutes()` — обед вычитается, см. ниже), а в Jira
    уходит только разница с уже затреканным. Отсюда стартовая позиция — уже затреканное время
    (через `positionFor()`, обратное к `workedMinutes()`; левее бегунок не пускается:
    «раз-трекать» нельзя), а заполнение двухцветное: зелёное до старта (уже в Jira) + синее
    до бегунка (добавится);
  - **обеденный перерыв** (`[worktime].lunch_start`/`lunch_end`, по умолчанию 12:00–13:00) —
    оранжевая полоса на ползунке (отдельный слой градиента поверх заполнения, видна и на
    пройденной, и на непройденной части) и **не идёт в трекинг**: `workedMinutes()` вычитает
    пересечение позиции с обедом. Внутри обеда бегунок не останавливается (отработанное там
    не растёт) — `normalizePosition()` перекидывает его через обед в сторону движения
    (сравнение с `lastValue`). Обед вне границ рабочего дня Config отключает (пустые строки),
    тогда `hasLunch === false` и ползунок ведёт себя как раньше;
  - **итог по центру ряда действий** — жирная надпись «Будет затрекано: 4 часа 15 мин»
    (`.worktime-summary`, формат — `formatHoursMinutes()` с русскими падежами часов, в отличие
    от `formatClock()` у индикатора и пузырька), между «Отмена» и «Затрекать»: показывает то, что уйдёт в
    Jira, уже без обеда. Вставляется в `.modal-actions` из `render()`, а не из `onRender` —
    кнопки `showModal()` создаёт после `onRender`, и раньше вставлять просто некуда;
  - пузырёк над бегунком в покое показывает затреканное за сегодня — оранжевым
    (`--warning`) при недоборе нормы `[worktime].daily_hours` и зелёным при норме и выше;
    при перетаскивании — синим `+Ч:ММ (сумма)`; под бегунком время дня (`formatTimeOfDay()`)
    в плоской пилюле — голый серый текст на светлом фоне модалки не читался. Пилюля
    подсвечивается по текущему времени машины пользователя: позиция позже «сейчас» — зелёная
    (`.worktime-clock--ok`), не позже — оранжевая (`.worktime-clock--warn`).
    Время читается в `render()`, а не при открытии модалки —
    за время работы с ползунком оно уходит вперёд;
  - границы заполнения и позиции подписей считаются в пикселях от центра бегунка (а не в
    процентах ширины): бегунок не выезжает за края трека, и проценты давали бы смещение стыка;
  - жёлоб высокий (18px), бегунок 26px намеренно выше жёлоба и выступает за него. Диаметр
    бегунка задан дважды — `TRACK_THUMB_SIZE` в `app.js` (по нему считаются позиции) и
    `::-webkit-slider-thumb`/`::-moz-range-thumb` в CSS: **меняя одно, меняй второе**, иначе
    пузырёк и пилюля времени разъедутся с бегунком;
  - перетаскивание, клик по треку и стрелки клавиатуры — **нативные**: свой drag-хендлер с
    замедлением тут был и убран осознанно, шага в 10 минут достаточно. `render()` (по событию
    `input`) только доводит значение до допустимого — граница затреканного и обед;
  - **вид ползунка строго плоский** (iOS / macOS Tahoe): сплошные цвета, никаких градиентов-
    бликов, внутренних теней и тени под бегунком — у бегунка только плоский контур
    (`--worktime-thumb-border`), чтобы белый круг не терял края на светлом фоне. Не добавляй
    сюда объём;
  - сама модалка светлее и шире обычной (`.modal:has(.worktime)` в `style.css`): плоские цвета
    ползунка на стандартной полупрозрачной поверхности сливаются с фоном за модалкой, а
    `max-width: 470px` с уменьшенными боковыми отступами (18px вместо 28px у `.card`) тянет
    трек почти на всю ширину окна 500×500 — от длины трека напрямую зависит точность попадания
    в нужные минуты. Тень у модалки остаётся общая (`--shadow`). Селектор по содержимому
    специально вместо параметра-модификатора в `showModal()` — это презентационное исключение

  - первый рендер — в `requestAnimationFrame`: `showModal()` показывает окно уже после
    `onRender`, у скрытого ползунка ширина нулевая и позиции посчитались бы неверно;
  - кнопка «Затрекать» заблокирована, пока добавлять нечего (`.btn:disabled`), после успеха —

## Безопасность — правила, которые нельзя отменять «для удобства»

Приложение персональное и без авторизации (осознанный YAGNI), поэтому вся защита строится на
одном допущении: доступ к нему есть только у хозяина машины. Всё ниже поддерживает именно это
допущение — если правку хочется сделать «чтобы открывалось с телефона» или «чтобы дёргать API
скриптом», сначала обсуди её, а не выключай проверку.

- **Наружу отдаются только `public/` и `api/`** — `router.php`, обязателен и в `Dockerfile`
  (`php -S ... -t /app /app/router.php`), и при ручном `php -S localhost:8000 router.php`.
  Документ-рут — корень проекта (фронт ходит в `../api/`), поэтому без роутера по HTTP
  скачивались бы `config/params.ini` с токенами Jira/нейронки, `storage/app.sqlite`, `.git` и
  `.idea`. Новый публичный каталог — новая запись в `ALLOWED_PREFIXES`, а не отказ от роутера.
- **Порт публикуется только на loopback** — `127.0.0.1:8000:8000` в `docker-compose.yml`.
  На `0.0.0.0` вся локальная сеть получала бы право читать задачи, трекать время в Jira,
  переводить статусы и жечь токены нейронки.
- **Каждый эндпоинт проверяет источник запроса** — `assertSameOrigin()` в `api/_bootstrap.php`
  (`Sec-Fetch-Site`, фолбэк по `Origin` против `Host`), вызывается один раз в бутстрапе, то
  есть новый эндпоинт получает защиту автоматически. Без неё любая открытая в браузере
  страница могла бы вслепую отправить POST на `localhost:8000/api/*` (`Content-Type:
  text/plain` не требует preflight, CORS такой запрос не останавливает) и удалить задачу или
  затрекать время. Токен/сессия здесь были бы избыточны — проверять нужно только источник.
- **Тексты ошибок PHP не уходят в браузер** — `display_errors = 0` в `src/bootstrap.php`
  (стектрейс содержит пути и аргументы, включая токены из `params.ini`). Смотреть ошибки —
  в логе сервера (`docker compose logs -f app`).
- **Ссылка на задачу — только `http`/`https`** (`TaskService::assertLinkSchemeIsWeb()`), потому
  что она сохраняется в БД и подставляется на фронте в `href`: строка вида
  `javascript:alert(1)/PROJ-1` тоже содержит ключ задачи. На фронте то же правило дублирует
  `safeHttpUrl()` в `app.js` — для записей, уже лежащих в БД.
- **Любая подстановка данных в HTML — через `escapeHtml()`** (экранирует и кавычки, поэтому
  безопасна внутри атрибутов), любой `href` — через `safeHttpUrl()`. Данные из Jira (заголовок,
  статус, ключ) — такой же недоверенный ввод, как введённый руками текст.
- **Конфиг в inline-скрипте кодируется с `JSON_HEX_*`** (`JSON_ENCODE_FLAGS` в
  `public/index.php`) — иначе строка `</script>` в `params.ini` разорвала бы тег.
- **Защитные заголовки страницы** — CSP (`default-src 'self'`, внешних ресурсов приложение не
  грузит вообще), `X-Content-Type-Options`, `Referrer-Policy` в `public/index.php`. Добавляя
  внешний ресурс (шрифт, CDN), сначала подумай, нужен ли он: сейчас CSP запрещает всё внешнее,
  и это правильное состояние для проекта без зависимостей.
- **SQL — только через prepared statements** (весь SQL живёт в репозиториях), путей из запроса
  в файловые операции не попадает, `shell_exec`/`eval` в проекте нет — так и держим.
- `config/params.ini` держим с правами `600` (см. README).
- **`ClaudeHooksService` — единственное место в проекте, где приложение пишет за пределы
  контейнера, в реальный файл на хосте** (`settings.json` Claude Code десктопного приложения).
  Поэтому в `docker-compose.yml` смонтирован volume-ом только этот один файл
  (`${HOME}/.claude/settings.json`), а не весь каталог `~/.claude` — там же токены MCP-серверов
  и история сессий, которым в приложении делать нечего. Расширяя эту фичу — не меняй эту
  границу на «смонтировать каталог целиком ради удобства».

## Запуск

См. `README.md`. Короткая версия: `docker compose up -d --build` (весь проект смонтирован
как volume — после `docker compose restart` подхватывается любой правленый файл, пересборка
образа нужна только при изменении `Dockerfile`).
